# Introduction

- A pretrained model knows a lot of language but does not behave like an assistant, does not use your company's tone, and does not reliably output your JSON format. Writing ever longer prompts helps only so far.
- Supervised fine-tuning shows the model a few thousand examples of exactly the behaviour you want and trains it to imitate them.
- Afterwards the learner can decide whether a problem needs fine-tuning or just a better prompt, describe what a good SFT data set looks like, and explain the two training tricks every SFT run uses: answer-only loss and packing.

# Core

Supervised fine-tuning continues next-token training on demonstrations:
conversations or prompt-response pairs that show the desired behaviour,
formatted with the model's chat template. Because the goal is to learn how
to answer, not how to write questions, the loss is usually computed only on
the assistant's tokens; prompt tokens are masked out. Many short examples
are packed into one long sequence to avoid padding. SFT is worth it when a
behaviour or format must be reliable, when a smaller model should do what a
larger one does with long prompts, or when the domain is unusual; a few
thousand clean, varied examples often beat a large noisy set. A run is
judged by generated samples on held-out prompts, not only by its loss.

# Key facts

- **Demonstration data**: (system,) user, assistant turns that show the target behaviour. Sources: human-written, filtered real conversations, or generated by a stronger model and reviewed.
- **Quality over quantity**: small curated sets can work well; the LIMA study (2023) fine-tuned a 65-billion-parameter model on 1,000 carefully selected examples. Duplicates, errors and inconsistent formats are learned too.
- **When SFT**: consistent format or style, behaviour a prompt cannot make reliable, a smaller or cheaper model for one job, or domain language. **When prompting is enough**: one-off tasks, fast-changing requirements, little data. Facts that change often belong in retrieval, not in weights.
- **Answer-only loss**: labels of prompt tokens are set to −100 (ignored by the loss), so only assistant tokens are trained. In a 300-token example with a 220-token prompt, 80 tokens carry the loss.
- **Packing**: concatenate tokenized examples, separated by the end-of-sequence token, into sequences of the maximum length, so almost no padding is needed. With 2,048-token sequences and 300-token examples, 6 whole examples fit in one sequence. Without separate attention masks per example, packed examples can attend to each other.
- **Typical settings**: 1 to 3 epochs, learning rate about 1 · 10⁻⁵ to 5 · 10⁻⁵ for full fine-tuning (around 10⁻⁴ for LoRA), warm-up, the model's chat template. In the TRL library `SFTTrainer` handles template, masking and packing.
- **Signals**: the training loss usually drops fast in the first few hundred steps and then flattens; a training loss near 0 with rising validation loss means memorisation. Watch generated samples on fixed held-out prompts at each checkpoint: format, correctness, refusals, repetition.
- **Forgetting**: SFT on a narrow task can make the model worse at other things (catastrophic forgetting); mixing in general data and short training reduce it.

# Level: highschool

<!-- ptf:text v1 -->

Imagine teaching a new employee to answer customer e-mails. You could hand
them a long rulebook every morning (that is prompting), or you could sit
with them for a week and go through a thousand real e-mails with
model answers. After that week they answer in the right tone without the
rulebook. That week is **supervised fine-tuning**, SFT for short.

For a language model the "model answers" are example conversations: a
user message and the ideal assistant reply, written in the model's chat
format. Training works like pretraining: guess the next token, compare,
adjust. With one twist: we only grade the model on the **assistant's
part**. The user's question is given; there is no point in teaching the
model to write customer questions. So the question's tokens are marked
"do not grade", and only the answer counts.

Quality beats quantity. A thousand clean, varied examples can teach a
style better than a hundred thousand messy ones, because the model copies
everything, including mistakes and sloppy formatting.

A practical trick called **packing** saves computing time: instead of
padding every short example to the maximum length, several examples are
put one after another into one long sequence, separated by an end marker.

How do you know it worked? Not by the loss alone. Keep a set of test
questions the model never trained on and read its answers after each
round. If the training loss gets close to zero while answers to new
questions get worse, the model is memorising the examples.

And sometimes you do not need SFT at all: if a good prompt already gives
reliable results, or the task changes every week, prompting is cheaper.

# Level: college

<!-- ptf:text v1 -->

Write down a decision rule before reading on: given a task, a model and a
budget, when would you fine-tune instead of prompting?

SFT maximises ∑ log p(y_t | x, y_{<t}) over demonstration pairs (x, y),
where x is the formatted context and y the assistant response, using the
chat template the model will be served with. Implementation: tokenize the
rendered conversation, build `labels` as a copy of `input_ids` with all
non-assistant positions set to −100, so cross-entropy ignores them
(TRL: assistant-only or completion-only loss). Masking prompts focuses
capacity on responses and avoids learning to imitate user text; for
multi-turn data every assistant turn is a target.

Packing concatenates examples (EOS-separated) into fixed-length rows,
removing padding waste; with a mean of 300 tokens and 2,048-token rows,
about six examples per row instead of one. Plain packing lets later
examples attend to earlier unrelated ones; packing with per-example
attention masks or position-ID resets (variable-length attention) avoids
that contamination.

Data matters more than hyperparameters: coverage of the target
distribution, consistency of format, correctness, and diversity. Small
curated sets (LIMA: 1,000 examples) can shift style and format
substantially because pretraining already supplies the knowledge: SFT
mostly selects behaviour. Knowledge injection through SFT is weak and
can increase hallucination on facts the model did not know; use
retrieval for changing facts.

Hyperparameters: 1–3 epochs, lr 1–5 · 10⁻⁵ (full) or ~10⁻⁴ (LoRA),
cosine or linear decay with warm-up, effective batch 32–128 sequences.
Monitor training and validation loss, but evaluate by generation on a
fixed held-out prompt set and task metrics; loss falling to near zero
on small data is memorisation. Mitigate forgetting with short runs,
lower learning rates, mixing general instruction data, or
parameter-efficient methods.

# Misconceptions

- **sft-adds-knowledge**: Fine-tuning on a few documents reliably teaches the model new facts → SFT mostly shapes behaviour and format; new or changing facts are better supplied by retrieval.
- **train-on-prompts**: All tokens of the conversation should count in the loss → usually only the assistant's tokens are trained; the prompt is context.
- **more-data-always**: More examples always beat fewer → quality, consistency and diversity matter more; noisy data teaches noise.
- **low-loss-good**: A training loss near zero means a great model → on small data it usually means memorisation; judge by answers to held-out prompts.

# Examples

- **New employee and model answers**: SFT is a week of practice with model answers instead of a rulebook (prompt). Breaks down: the employee understands why; the model imitates patterns.
- **Covering the question, grading the answer**: answer-only loss is like a teacher who marks only the answer section of a worksheet.

# Tutor notes

- Start by asking the learner when they would train instead of prompt; their answer shows whether they think SFT adds knowledge (a common misconception).
- If the learner did the fine-tuning-workflow step, SFT is the same loop on conversations; spend the time on data quality and answer-only loss.
- Learners who code: a small SFT run with TRL on a few hundred examples of a fixed format is a good project, ideally with LoRA (next step) to fit on one GPU.
